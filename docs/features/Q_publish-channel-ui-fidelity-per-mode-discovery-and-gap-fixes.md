# Q: Publish channel UI fidelity: per-mode discovery and gap fixes

## Goal

Every publish-channel plugin must match the real platform UI, per publishing mode, instead of the behaviour inherited from the `wt` skills. This feature captures first-hand UI evidence for every (platform, mode) pair — entry URL, ordered step sequence, control inventory with selectors, the success signal actually observed, the draft-vs-publish affordances, and the drift against the plugin's current constants — and then fixes the gaps it finds, so each channel can save a draft and publish only on explicit operator request.

The mode architecture is settled by this feature's own evidence: **one plugin per channel, modes as first-class validated `operation`s** (x-pub `post|article` is the existing precedent), because every mode on a platform shares one login/profile/session. Separate plugins are only warranted by a different account, a different `Content → Result` contract, or a different product surface.

## Scope

**In scope**

- Per-mode UI discovery from the live console using the operator's own authenticated profile, draft-only, for: `xhs` (上传视频, 上传图文, 写长文, 发播客), `x` (article, post/tweet), `wechatmp` (图文草稿), `infoq` (write/draft), `juejin` (draft), `substack` (post draft).
- One evidence record per (platform, mode) plus one curated tracked design doc per platform, including the drift list against the plugin's current constants.
- Mode dispatch: `operation` on the Content metadata / invoke options, validated per channel, with a named fast-fail before any browser opens.
- Gap fixes: corrected entry URLs, selectors, step order and success signals; per-mode modules inside the channel plugin; one shared profile/session/preflight per channel.
- Preserving the channel `profile-check login|check` CLI and its profile-dir precedence tiers.

**Out of scope**

- Live publishing during discovery or CI — discovery and dogfood save drafts only; public publishing stays operator-explicit.
- Any xhs automation beyond the ADR-025 budgets (one `check` and one publish cycle per 2 h).
- New channels beyond the listed set, and the API/CLI transports (medium, qiita, zenn) which need no browser flow.
- Upstreaming the shared browser library into `@gobing-ai/ts-browser-automation`.
- Authoring/generation concerns (how a long article or an image set is produced) — those stay in generators and workflows.

## Acceptance Criteria

```gherkin
Feature: Publish channel UI fidelity

  @core
  Scenario: R1 — Every platform mode carries recorded UI evidence with its drift findings
    # covers: I1, I2
    Given a publish channel in the discovery set and each of its publishing modes
    When the operator-authenticated console is walked once, draft-only
    Then an evidence record exists for that (platform, mode) pair
    And it names the entry URL, the ordered step sequence, the verified selectors, the observed success signal and the draft-vs-publish affordances
    And it lists each difference from the plugin's current constants

  @core
  Scenario: R2 — A channel exposes its modes as validated operations and refuses an unknown one before opening a browser
    # covers: I3
    Given a channel plugin with two or more publishing modes
    When a run requests a mode that the channel does not support
    Then the run fails with a named unsupported-operation error
    And no browser is launched and no profile is resolved

  @core
  Scenario: R3 — Each corrected flow saves a draft through the real console with an observed signal
    # covers: I4
    Given a logged-in profile for a channel and a Content for one of its modes
    When the channel runs in draft mode
    Then the console shows the saved draft and the Result carries the observed draft URL or id
    And a run whose signal never appears returns ok false naming the missing signal

  @core
  Scenario: R4 — Discovery and tests never touch a publish control
    # covers: I5
    Given any discovery walk or automated test in this feature
    When the flow reaches the save/draft affordance
    Then the run stops there and no publish, submit or send control is clicked
    And the evidence records where that control lives without activating it

  @core
  Scenario: R5 — Recorded gaps are fixed or explicitly excluded with a reason
    # covers: I2, I6
    Given the drift list captured for a channel
    When the channel's fix work completes
    Then every recorded gap is either corrected in the plugin or listed as an out-of-scope exclusion with its reason
    And the channel's draft path is exercised against the observed evidence
```
