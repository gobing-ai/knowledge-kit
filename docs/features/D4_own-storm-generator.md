# D4: Own STORM generator

## Goal
Replace the D2 stand-in with an owned Bun/TypeScript STORM pipeline that performs curation, outline generation, grounded article generation, and polishing behind the existing `ContentGeneratorPlugin` contract.
## Scope
- In: replace the internals of `plugins/generations/content-gen` with a four-stage STORM pipeline; reuse the existing `spur agent run` boundary once per stage; ground research and citations only in the supplied `Doc[]`; preserve the current `Doc[] → Content` invoke contract and failure semantics; add deterministic stage-boundary and end-to-end contract tests.
- Out: Python or DSPy at runtime; a direct LLM-provider transport; external-web retrieval; new plugin kinds or schemas; `Brief`/`GeneratorInput` contract widening; publish-channel work.
## Acceptance Criteria
```gherkin
Feature: Own STORM generator

  @core
  Scenario: R1 — The owned STORM pipeline runs behind the existing generator contract
    Given a non-empty valid DocList input
    When knowledge-kit invokes the content-gen plugin
    Then curation, outline, article, and polish stages run in order
    And the output parses against ContentSchema

  @core
  Scenario: R2 — Curation builds multiple grounded perspectives from supplied documents
    Given source documents treated as untrusted content
    When the curation stage develops perspectives and questions
    Then its structured result contains evidence traceable only to the supplied document IDs
    And it performs no external retrieval

  @core
  Scenario: R3 — Outline generation uses the curated evidence
    Given a valid curation result
    When the outline stage runs
    Then it emits a structured markdown outline derived from that result

  @core
  Scenario: R4 — Article generation grounds sections and citations in supplied documents
    Given a valid outline and curated evidence
    When the article stage writes the draft
    Then each emitted citation maps to a supplied document
    And Content references use available Doc sourceUri, title, and id fields

  @core
  Scenario: R5 — Polishing preserves structure and produces contract-valid Content
    Given a grounded draft article
    When the polish stage runs
    Then the final markdown preserves headings and citations while removing repetition
    And Content includes body, outline, references, and STORM provenance metadata

  @core
  Scenario: R6 — The owned pipeline replaces the stand-in without widening the platform seam
    Given the existing content-gen manifest and DocList-to-Content contract
    When D4 is implemented
    Then the wt technical-content-creation stand-in is no longer invoked
    And no Python runtime, direct LLM-provider client, plugin kind, or schema is added

  @edge
  Scenario: R7 — Empty input retains the generator notice contract
    Given an empty DocList
    When the content-gen plugin runs
    Then it writes notice Content with empty references and exits zero

  @edge
  Scenario: R8 — A failed or malformed stage fails loud
    Given any stage exits non-zero or returns malformed structured output
    When the pipeline propagates the failure
    Then the plugin emits a stage-specific diagnostic and exits non-zero
    And no stale output file remains

  @edge
  Scenario: R9 — Sparse document metadata remains schema-valid
    Given source documents without titles or source URIs
    When the pipeline maps the final Content
    Then optional reference fields are omitted and provenance still carries document IDs
```
