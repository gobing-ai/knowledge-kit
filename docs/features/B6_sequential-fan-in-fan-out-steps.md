# B6: Sequential fan-in/fan-out steps

## Goal
kk-owned sequential fan-in and fan-out step semantics: `kk fanin` (N `docs.json` → 1 merged Doc list with primary-id dedupe + `metadata.sources` provenance) and `kk fanout` (1 `content.json` → N publishers, aggregate Result with per-target status, exit 1 on partial failure). Spec: `docs/design/fan-in-and-fan-out-specification.md` (task 0033). Implementation graduates here once map J closes.
## Scope
- In: `kk fanin` / `kk fanout` CLI surface (siblings of `kk invoke`, ADR-006 boundary); merge + aggregate Result schemas; `--retry-from` state skipping.
- Out: engine-level parallelism (deferred, ADR-007 R4); DAG runtime.
## Acceptance Criteria
```gherkin
Feature: Sequential fan-in/fan-out steps

  Scenario: Fan-in merges many document sets into one
    Given two ingestion outputs that share one document id
    When `kk fanin --in a.json --in b.json --out merged.json` runs
    Then merged.json contains that document exactly once
      And its metadata.sources lists both originating sources

  Scenario: Fan-out reports per-target outcomes
    Given one content.json and five publish targets where two fail
    When `kk fanout --content content.json --target ... --out result.json` runs
    Then result.json records five per-target entries with two marked failed
      And the process exits non-zero

  Scenario: Retry targets only prior failures
    Given a result.json from a run with two failed targets
    When `kk fanout --retry-from result.json` runs
    Then only the two previously failed targets are dispatched
```
