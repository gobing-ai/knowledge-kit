# C1: Ingestion plugin design

## Goal
Produce the plugin-instance authoring contract with ingestion as the proving kind: how a plugin declares source config, how `kk invoke` passes config to the entry, Doc-mapping conventions (id stability, sourceUri/mediaType, metadata), and failure semantics. Delivered as a design doc; promote to `@gobing-ai/kk-core` only what C2 actually consumes. Lands before C2; the generic half is the shared contract D3 (generator design) cites rather than re-derives.
## Scope
- In: source-config declaration mechanism (flags vs manifest key vs config file vs env), decided and documented; `--in` semantics per source type plus the extra-config channel through `invoke` (or an explicit follow-up if the channel does not exist); Doc mapping conventions including id stability across re-runs; failure semantics (empty output, partial item failure, diagnostics channel, exit codes); FS-source and API-source patterns; secrets-via-env statement; generic vs ingestion-specific split so D3 cites the generic half; validation against the as-built B1/B2 platform (registry, kindContract, runInvoke).
- Out: any concrete source implementation (C2+); incremental-sync state (C2); DAG runtime (deferred per ADR-006); changes to Doc/Content/Result schemas (ADR-level decision, not this feature); generator-specific contract details (D3).
## Acceptance Criteria
```gherkin
Feature: Ingestion plugin design

  Scenario: Source config declaration is specified
    Given the as-built manifest schema and invoke engine
    When the design names where per-plugin source config lives
    Then an FS source and an API source can both be configured without code changes to invoke

  Scenario: Invoke integration contract is specified
    Given kk invoke spawns an ingestion entry with --in/--out
    When the design defines --in semantics and the extra-config channel
    Then a plugin author can predict argv/env for any supported source type

  Scenario: Doc mapping conventions are specified
    Given the Doc schema in kk-core
    When the design defines id stability, sourceUri, mediaType, and metadata usage
    Then re-running an ingestion plugin over unchanged input yields stable Doc ids

  Scenario: Failure semantics are specified
    Given the fail-loud mandate of ADR-006
    When the design covers empty output, partial item failure, and diagnostics
    Then each case has an explicit exit-code and output-file contract

  Scenario: Generic contract is reusable by other kinds
    Given the design separates generic plugin-instance concerns from ingestion-specific ones
    When D3 (generator design) starts
    Then it can cite the generic half instead of re-deriving it

  Scenario: Design is validated against the platform as built
    Given registry, kindContract, and runInvoke as implemented
    When the design is reviewed against them
    Then no requirement contradicts B1/B2 behavior without an ADR entry
```

- Open questions the design must resolve:
  - Config channel: CLI flags vs manifest key vs config file vs env vars (manifest is currently `{name, kind, entry, version?, description?}` + passthrough; no product config file exists).
  - `--in` semantics per source type, and how extra config reaches the entry (invoke currently spawns with only `--in`/`--out`).
  - Doc `id` derivation for stability across re-runs (downstream dedup depends on it; C2 defers incremental-sync state).
  - Empty-output semantics: `DocListSchema` accepts `[]` — success or failure?
  - Partial item failure policy (skip-with-warning vs fail) and diagnostics channel (stderr vs sidecar).
  - Secrets channel for API sources: env inheritance into the spawned entry, never in the manifest.
  - Where the design doc lives (docs/ vs plugins/kk/ authoring guide).
