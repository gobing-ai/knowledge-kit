# E8: Xiaohongshu image-card authoring and publishing

## Goal

Turn source content into a coherent Xiaohongshu image-card post and publish it through the existing `kk` image and XHS surfaces with an honest, verifiable result.

## Scope

**In scope**

- Analyze a supplied article or note into an ordered XHS card plan with a cover and content cards; keep card copy grounded in the source.
- Add XHS format/style presets and a `kk` authoring skill that uses the existing `image-gen` provider, preview, budget, and artifact path.
- Preserve an ordered card manifest, exact prompts, generated image paths, and a Chinese note as a valid `Content` payload for `xhs-pub`.
- Make `xhs-pub` consume and attach that ordered image set, prepare an actual draft, and support explicitly requested live publication through its existing browser/agent transport boundary.
- Return a truthful `Result`: distinguish prepared draft from live publication, retain platform identity where available, and fail on missing images, login problems, or incomplete submission.
- Use the vendored Baoyu skill as a source for card planning and style guidance while retaining this project's existing preference and provider contracts.

**Out of scope**

- A second product generator plugin or duplicate image provider stack.
- Replacing the existing `image-gen` jobs, preset resolution, or global preference hierarchy.
- Silent live publication, platform growth claims, or guaranteed text fidelity from a model.
- Multi-channel publishing changes outside the XHS path.

```gherkin
    When the authoring skill renders the plan
    Then each ordered card has an image artifact and its exact saved prompt
    And the rendering uses the existing image-gen provider, one series spend confirmation, and a series-total image cap

  @core
  Scenario: R3 — Card series becomes a publishable XHS payload
    # covers: I1, I2
    Given an ordered rendered card series and a Chinese note
    When the authoring skill prepares the XHS post
    Then it writes valid Content with the note and image paths in card order
    And the payload can be read by xhs-pub without reconstructing card order from filenames

  @core
  Scenario: R4 — XHS publisher creates a draft with the ordered images
    # covers: I2
    Given a valid XHS payload with two image files and an authenticated browser session
    When xhs-pub prepares a draft
    Then both images are attached in payload order and the editor shows two images
    And the Result identifies the outcome as an unpublished draft only after the draft save is observed

  @core
  Scenario: R5 — Explicit live request publishes the XHS post
    # covers: I2
    Given a complete XHS draft and an explicit live publication request
    When xhs-pub submits the post
    Then the Result reports live publication only after the browser confirms success
    And it records the platform identity or URL when available

  @edge
  Scenario: R6 — Missing or failed images prevent a false publish result
    # covers: I1, I2
    Given an XHS payload with a missing image or a browser attachment failure
    When xhs-pub processes the payload
    Then it returns a failed Result naming the failed image or action
    And it does not report a draft or live publication

  @edge
  Scenario: R7 — Rendering failure preserves the successful card prompts
    # covers: I1, I4
    Given saved prompts for a card series and a provider failure on one card
    When the authoring skill reports the rendering failure
    Then the failed card can be retried from its saved prompt
    And successful card images are not regenerated solely to retry that card
```

## Notes

- 2026-09-25 refinement: `xhs-pub` switches to the `script` driver for XHS (overrides E7 design D4 for this channel only; ADR-024). The `agent` driver has no evidence channel back into `Result`.
- The series budget is enforced by the skill against the total card count, because `image-gen`'s cap is per invocation.
- The exact prompt is the `KK_IMAGE_DRY_RUN=1` `Content.body` per card. Retry reuses the per-card `--in` envelope on the same `--out`.
- Runtime prerequisite for live/draft posting: `playwright` + Chromium on the kk install (kept external by the bundler).
