# F616: Legible XHS card text via deterministic typesetting

## Goal

**Card copy must be readable, and today it never is.** The on-card Chinese text is generated as
*pixels* by a diffusion image model (MiniMax `image-01`), which has no glyph renderer: the measured
result was that every Chinese string came back illegible. Root cause is structural, not a prompt
weakness — BPE token embeddings carry no glyph geometry and latent compression destroys the 2-5px
strokes of a Han character, so MiniMax `image-01` is documented as failing CJK outright while the
repo's own daily-cover design (task 0163) already forbade putting Chinese text in an image prompt.
The `xhs-card` format does exactly that forbidden thing.

Fix: stop asking an image model to be a typesetting engine. Set card copy from a real font with a
deterministic renderer, optionally over a **text-free** model illustration.

## Scope

**In scope**

- A deterministic text-composition step for the `xhs-card` format: headline and bullet points set
  from a real font at the declared 1080x1440 canvas, with a bounded safe area and a minimum glyph
  size.
- A text-free illustration contract: the model prompt may describe scene and style but must request
  no letters, numerals, or Chinese characters.
- Wiring into `kk stage daily-xhs-render` and the `kk:xhs-images` skill, plus the legibility
  assertion and the missing-glyph failure path.

**Out of scope**

- Switching to a CJK-stronger provider (e.g. `qwen-image-2.0-pro`) as the sole remedy: it needs a
  new credential and remains probabilistic, so it is a fallback, not the fix.
- Repairing bitmap text inside already-generated images.
- Any change to `xhs-pub` transport or the ADR-025 automation guard.

## Acceptance Criteria

```gherkin
Feature: Legible XHS card text via deterministic typesetting

  @core
  Scenario: R1 — Card copy is set with real type, not generated pixels
    Given a card plan with a Chinese headline and bullet points
    When a card is composed
    Then the on-card text is rendered from a real font by a deterministic text engine
    And no image-generation provider receives the card copy in its prompt

  @core
  Scenario: R2 — The declared canvas is the delivered canvas
    Given the xhs-card format declares a 1080x1440 portrait canvas
    When a card is composed
    Then the emitted image is exactly 1080x1440
    And text stays inside a bounded safe area with a minimum rendered glyph size

  @core
  Scenario: R3 — Composition is deterministic and resumable
    Given the same card plan rendered twice
    When the composer runs again
    Then identical input yields identical output, so a recorded artifact is reused
    And a resume renders only the cards whose artifacts are missing

  @edge
  Scenario: R4 — Missing font coverage fails loud
    Given card copy containing a character absent from the selected font
    When the card is composed
    Then the composer fails naming the character rather than emitting tofu or a substitute

  @edge
  Scenario: R5 — The illustration layer stays text-free
    Given an optional model-generated illustration for a card
    When its prompt is composed
    Then the prompt requests no letters, numerals, or Chinese characters
    And the composed card remains legible if that illustration is absent
```
