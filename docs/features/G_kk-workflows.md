# G: kk workflows

## Goal

Collection parent for kk product workflows (`plugins/kk/workflows/*.yaml`) and the workflow infrastructure they share. One child per workflow (G1 kk-daily-ai-voice, G2 kk-itc, G3 kk-collect, G4 kk-solo-podcast, G5 kk-storm-research, G6 kk-ingest-generate-publish); cross-workflow capabilities (run ledger) get their own child (G7). Mirrors the kind-parent pattern of C/D/E/F.

## Scope

- In: workflow YAML under `plugins/kk/workflows/`, the `kk` steps a workflow owns end-to-end, workflow-shared infrastructure (store, ledger, schedules); one child per workflow, grandchildren per change.
- Out: plugin instances (C/D/E), `plugins/kk` agent capabilities (F), engine/runtime work in ts-libs or spur, example workflows (`*-example.yaml`).

## Acceptance Criteria

```gherkin
Feature: kk workflows

  @core
  Scenario: R1 — Every product workflow has a child node
    Given a top-level product workflow YAML under plugins/kk/workflows/ that is not an example (`*-example.yaml`)
    When the feature tree is listed
    Then exactly one direct child of G is its home: the child named after the workflow, or — for a versioned successor — the child whose Goal names the workflow's file
    And a nested sub-workflow (one another workflow runs via `spur workflow run plugins/kk/workflows/<name>.yaml`) is homed with the workflow that runs it

  @core
  Scenario: R2 — Workflow-shared capabilities have their own child
    Given a kk command family invoked by more than one product workflow that is workflow infrastructure (not the generic `executor`, `package` or per-workflow `stage` surfaces)
    When it is planned as a feature
    Then exactly one direct child of G claims it in its Scope
    And that child is its own capability child (not named after a workflow), unless one workflow owns the capability by filling it — then it stays with that owner's child, and the other workflows only select from it or mark what they used
```
