# R: image-gen-runtime-fallback

## Goal

Make image generation survive a configured provider failing mid-flight, under explicit operator opt-in. Selection-time `AUTO_ORDER` (0103) already picks the first *configured* provider; this adds **runtime** fallback for *execution* failure, with error classification so auth/quota exhaustion is loud before a second vendor is charged and content-policy rejections never silently re-prompt another provider. Strictness stays the default: absent `fallback`, behavior is exactly today's fail-fast (0103 no-silent-downgrade rule preserved).

## Scope

**In scope**

- Opt-in `fallback` field on the image-gen job envelope: absent = current strict behavior; `true` = on provider execution error, retry down `AUTO_ORDER` (skipping `NEVER_AUTO` and the failed provider); explicit ordered list (e.g. `["google","zai"]`) = retry in exactly that order.
- Provider error classifier (auth / quota / transient / policy / unknown) driving retry decisions and log loudness.
- `runJob` retry loop: WARN log naming failed provider, error class, and next provider **before** any paid retry; artifact metadata records failed attempts + winner.
- `daily-cover` stage opt-in: workflow var `cover_fallback` (default absent) written into the built envelope — this is the daily news-cover use case.
- `docs/04_DESIGN.md` § image-gen envelope surface row, same commit as code (T3).

**Out of scope**

- Per-provider budgets, cost caps, rate-limit coordination (later increment).
- Harness image tools (`image_gen` / `generate_image`) — kk pipeline only.
- Changes to selection-time `AUTO_ORDER` / `NEVER_AUTO` semantics or strict selection errors.
- Automatic (non-opt-in) fallback of any kind.
- Fallback for non-image plugin kinds.

## Acceptance Criteria

```gherkin
Feature: image-gen runtime fallback — opt-in multi-provider retry

  @core
  Scenario: No fallback field keeps today's strict failure
    Given a cover job with provider "minimax" and no fallback field
    When the provider call fails with an auth error
    Then the job fails with the original error
    And no other provider is attempted or charged

  @core
  Scenario: fallback true retries down AUTO_ORDER after a loud log
    Given a job with fallback true and provider "minimax"
    When minimax fails with an auth or quota error
    Then a WARN log names minimax, the error class, and the next provider before any retry
    And the next provider in AUTO_ORDER (never one in NEVER_AUTO) is attempted
    And success records the winning provider and the failed attempts in artifact metadata

  @core
  Scenario: Explicit fallback list is honored in order
    Given a job with fallback ["google", "zai"]
    When the requested provider fails with a retryable error
    Then providers are attempted in exactly the listed order

  @core
  Scenario: Content-policy rejections never fall back
    Given a job with fallback true
    When the provider returns a content-policy rejection
    Then the job fails with the classified reason and no second provider is called

  @core
  Scenario: Exhausted fallback order fails loudly
    Given a job whose fallback order is exhausted
    Then the job fails listing every attempted provider with its error class

  @core
  Scenario: Explicit unknown or unconfigured provider still throws at selection
    Given a job requesting a provider that is unknown or not configured
    Then selection throws naming the provider and its required env (unchanged by this feature)
```
