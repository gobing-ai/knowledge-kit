# E93: kk plugin check / login — live channel readiness probe (ADR-032)

## Goal

An operator can answer "can this channel publish right now?" for every publish channel with one `kk plugin check`, and fix a stale session with `kk plugin login <name>`, without knowing per-plugin script paths (ADR-032).

## Scope

**In scope**

- Optional `check` field in `plugin.json` (entry path relative to the plugin dir), validated by the kk-core manifest schema and carried on `PluginRecord`.
- `kk plugin check [<name>…] [--kind <kind>] [--json] [--headed] [--timeout <ms>]`:
  - Spawns each selected plugin's probe as `<entry> check` with the operator-config env that `kk executor run` already uses.
  - Parses the final stdout JSON line `{ status, profileDir?, detail }` and prints one verdict row per plugin.
  - Plugins without the field report `unsupported`.
  - Exits nonzero when any probe refuses or errors.
- `kk plugin login <name>`: runs `<entry> login` interactively (inherited stdio) and exits with its code.
- The six browser channels expose the ADR-032 R4 contract:
  - infoq, juejin, substack and x already run on `runProfileCli`; they only need the manifest field and `--headed` passthrough.
  - xhs-pub and wechatmp-pub profile-check need the final JSON line, exit codes 0/1/2 and `--headed`.
- Docs in the same change as the surface:
  - `docs/04_DESIGN.md`: the `plugin` noun section, the manifest field, and the probe contract.
  - `docs/05_FEATURES.md`: the feature row.
- An E2E check over a fixture plugin with a fake probe, writing a JSON artifact. Then one operator live run against the real profiles.

**Out of scope**

- Any change to `kk plugin status`. It stays static: discovery plus entry health (ADR-032 R2).
- Credential probes for API channels (qiita, medium, x post, podcast, emdash, surfdash, zenn). They can opt in later through the same field.
- Running `check` from a workflow preflight; a follow-up can gate on `--json`.
- Fixing channel selector drift (0193/0194 own that).

## Acceptance Criteria

```gherkin
Feature: kk plugin check / login — live channel readiness probe (ADR-032)

  @core
  Scenario: R1 — plugin check reports one verdict per plugin that declares a probe
    Given plugins whose plugin.json declares a check entry
    When the operator runs kk plugin check, optionally with names, --kind or --json
    Then each selected plugin's probe runs as "<entry> check" with the operator-config env
    And each plugin reports verified or refused with the probe's detail line
    And the command exits 0 only when every probed plugin is verified

  @core
  Scenario: R2 — plugins without a probe report unsupported and never fail the run
    Given a plugin whose plugin.json declares no check entry
    When kk plugin check selects it
    Then it is reported as unsupported
    And it does not change the exit code

  @core
  Scenario: R3 — a broken probe is reported as an error, not as verified
    Given a probe that exits 2, crashes, times out, or prints no final JSON line
    When kk plugin check runs it
    Then the plugin is reported as error with the exit code or reason
    And the command exits nonzero

  @core
  Scenario: R4 — check is read-only and secret-free
    Given any probe run through kk plugin check
    When the operator runs kk plugin check with or without --headed
    Then it is headless unless --headed is passed
    And kk prints only status, profile dir and detail, never raw probe stdout, cookies or tokens

  @core
  Scenario: R5 — plugin login runs the plugin's interactive login
    Given a plugin that declares a check entry
    When the operator runs kk plugin login <name>
    Then "<entry> login" runs with inherited stdio and kk exits with its exit code
    And a plugin without a check entry is rejected with a usage error naming the missing field

  @core
  Scenario: R6 — the six browser channels implement the probe contract
    Given infoq-pub, juejin-pub, substack-pub, x-pub, xhs-pub and wechatmp-pub
    When their manifests and probe entries are inspected
    Then each plugin.json declares check
    And each probe accepts check, login, --profile, --timeout and --headed, exits 0, 1 or 2, and ends check output with one JSON verdict line

  @core
  Scenario: R7 — plugin status stays static
    Given the same plugin tree
    When the operator runs kk plugin status
    Then no probe is spawned and the output contract is unchanged, apart from listing the check field
```
