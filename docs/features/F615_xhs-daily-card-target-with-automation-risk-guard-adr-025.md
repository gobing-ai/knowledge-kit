# F615: XHS daily card target with automation-risk guard (ADR-025)

## Goal

The daily AI news pipeline can turn the lead news item into a Xiaohongshu image-card draft, with the
console-driving channel **off by default** and hardened after XHS warned the operator about automated
login/publish activity (2026-09-28).

## Scope

**In scope**

- The `xhs-write` / `xhs-publish` workflow pair: lead-item card planning, pinned `xhs-card` x
  `xhs-knowledge` render, ordered `Content` packaging, and the `xhs-pub` handoff.
- `kk stage daily-xhs-render` and `kk stage daily-publish-xhs`, including resume-safe per-card
  rendering and per-status result caching.
- `xhs_enabled: "false"` as the shipped default, and XHS as an independent non-blocking target that
  never contributes to `publish_status`.
- ADR-025: the headless session preflight and the 24h publish/check caps in `xhs-pub`.

**Out of scope**

- Card text fidelity — filed as F616.
- The image-gen canvas contract — filed as F617.

## Acceptance Criteria

```gherkin
Feature: XHS daily card target with an automation-risk guard

  @core
  Scenario: R1 — The daily pipeline prepares and publishes an XHS card draft from the lead item
    Given a published daily run with xhs_enabled=true and a rendered card series
    When the xhs-write and xhs-publish states run
    Then the series is planned from plan.json item 1 and rendered through pinned xhs-card presets
    And xhs-pub receives Content whose metadata.images are the card artifacts in card order
    And the Result distinguishes a draft from a live post

  @core
  Scenario: R2 — No headed console visit without a verified session
    Given a publish request whose saved profile is absent or unauthenticated
    When xhs-pub prepares the publish
    Then a headless session preflight refuses with a named reason
    And no headed browser is opened and no draft or post is reported

  @core
  Scenario: R3 — Console visits are rate-capped
    Given a publish or check already recorded inside the 24h window
    When the same event is attempted again
    Then the attempt is refused before any browser opens, naming the wait
    And a refused preflight leaves the publish window intact for a retry after login

  @edge
  Scenario: R4 — The guard fails closed
    Given an unreadable or unparsable automation state file
    When a publish is attempted
    Then it is refused with an actionable reset instruction
    And a fresh budget is never granted silently

  @edge
  Scenario: R5 — XHS never affects the episode's publication contract
    Given an XHS publish that fails, is capped, or is skipped
    When the run classifies its publish outcomes
    Then publish_status still reflects only surfdash and podcast
    And the run continues to completion
```
